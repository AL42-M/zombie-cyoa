CAPTAIN'S LOG

PROJECT WORKING INSTRUCTIONS

Purpose
- This file holds permanent working rules and concise project history so future
  agents can continue without asking the user to explain previous work.
- Read these instructions and relevant version entries before making changes.
- .github/copilot-instructions.md directs supported Copilot agents to this file.

Working with the user
- The user is relatively new to GitHub, Git, and software-development workflows
  and primarily builds projects by describing requirements to coding agents.
- Work autonomously on routine programming and implementation decisions.
- Explain unfamiliar Git/GitHub terminology in plain language when it affects
  something the user needs to understand or decide.
- Before requesting a decision, explain what the operation will do and the
  practical consequences. Do not over-explain routine work.
- Ask only when a meaningful choice substantially affects behavior, safety, or
  maintainability, or when work cannot proceed safely.

General behavior
- When a change is requested, inspect the project, determine the best
  implementation, make the change, and verify that it works.
- Before editing, read this file, inspect relevant project files, and check
  current Git state/history when useful.
- Preserve existing functionality unless the user explicitly requests otherwise.
- Do not silently remove features, data, or functionality to simplify a change.
- Respect existing uncommitted work; do not overwrite or revert unrelated edits.
- Suggested next steps in this log are context, not authorization to start
  additional work beyond the user's current request.

Versioning
- Use simple numeric versions: vMAJOR.MINOR, such as v0.1, v1.0, or v1.1.
- New projects begin at v0.1. Use v0.x during initial development.
- The first version considered complete and usable becomes v1.0; do not declare
  that milestone without evidence that the project is ready.
- Increment MINOR for normal development changes: features, bug fixes, UI,
  gameplay, quality-of-life improvements, and other ordinary modifications.
- Increment MAJOR only for significant milestones or substantial changes.
- Do not increment versions for inspections, commands, or discussion alone.
  A version increment represents an actual project modification.
- Never reuse or overwrite a previous version number.
- When incrementing, update any version displayed or stored by the application,
  if applicable, and add a corresponding entry to this log.
- Commit completed changes with a concise description.
- Do not make duplicate versioned or backup project files (for example,
  game-v1.2.html or game-final-final.html). Git history preserves prior versions.

Maintaining this log
- Update this file after meaningful project changes.
- Each version entry should include, where relevant: version number, summary,
  important implementation decisions, reasons for non-obvious decisions, known
  bugs or limitations, useful technical details, unfinished work, and next steps.
- Keep entries concise and useful to a future agent.
- Do not log routine file reads, searches, Git status checks, ordinary commands,
  successful routine tests, or minor intermediate edits.
- If an investigation or failed approach reveals something important, record
  the conclusion rather than a step-by-step transcript.

Git and source control
- Use Git as the authoritative project history.
- Create clear, concise commits representing completed logical changes.
- Do not rewrite or destroy useful history without explicit user permission.
- Never merge branches without explicit user authorization.
- Never force-push without explicit user authorization.
- Do not delete branches containing unmerged work without explicit permission.
- Stop and ask before potentially destructive Git operations.
- A commit saves a local checkpoint; a push uploads commits to GitHub. They are
  separate operations. Respect requests to review files before pushing.
- Do not assume permission to push from permission to edit or commit.

Safety and verification
- After modifying functionality, verify the project using appropriate available
  tests, builds, or runtime checks.
- Fix problems caused by your changes before calling the work complete.
- If work risks damaging existing changes or data, explain and ask before
  performing the destructive action.
- State incomplete work, blockers, and known limitations plainly.

Execution location and local copies
- The user controls creation of local copies of this repository. Do not clone,
  download, or otherwise create a new local copy on the user's computer without
  the user's explicit authorization for that copy. This also applies to new
  worktrees, child sessions, and tools that automatically prepare local copies.
- Permission to inspect or change code, push, open a pull request, or merge does
  not authorize creating a local copy. Do not bypass this rule through another
  agent, tool, archive download, or automatic fallback from cloud to local.
- Existing local workspaces may be used for work the user requests there. Do not
  delete or relocate them to enforce this rule.
- At the start of a task, state whether execution is on the user's computer, in
  a confirmed GitHub-hosted cloud environment, or on another remote host. Base
  this on available session/host evidence, not the app name or GitHub access.
- If execution location cannot be confirmed, say so and ask before creating a
  workspace or starting work that the user expects to continue while offline.
- A user-requested cloud task may check out the repository within its hosted
  environment; this does not authorize a copy on the user's computer.
- These instructions guide agents after they can read the repository. They
  cannot prevent an app or platform from preparing a workspace before loading
  them; the user must also control workspace creation in the app.

Cloud handoffs
- A local session cannot continue while its host laptop is off or asleep.
- A cloud task works from files uploaded to GitHub, not unpushed local changes
  or instructions that exist only in another session's conversation.
- When a handoff is requested, record completed work, remaining work, important
  decisions, and clear next steps here. Identify the branch the cloud task
  should use when reporting the handoff to the user.
- Uploading a branch does not start a cloud task or merge changes into main.
- Do not claim a cloud task was launched unless its launch is confirmed.

PROJECT CONTEXT

- Repository: AL42-M/zombie-cyoa.
- Game title: THE HUSH, a choice-driven zombie survival-horror browser game.
- Active game files are in ZombieChoiceAdventure. The entry point is index.html;
  style.css controls presentation, engine.js handles gameplay, audio.js handles
  audio, and story-*.js files hold the narrative.
- The game uses plain HTML, CSS, and JavaScript. Its title screen states that
  progress is stored in the player's browser.
- _audit.js is an existing Windows Script Host/JScript story validation harness;
  its header documents running it with cscript //E:JScript.
- ZombieChoiceAdventure-1.0-donottouch.zip is the original uploaded archive,
  renamed at the user's request. Preserve it unchanged; do not regenerate or
  overwrite it. Work in the active source folder and use Git for history.

VERSION HISTORY (newest first)

v1.2 - 2026-10-15
- Reworked the story into one-way passages: opening conversations now lead to
  Teddy's council rather than returning to the same stockroom menu; route
  detours and hospital investigations no longer send the reader back to a
  passage they have already read in the same run.
- Added distinct consequences for spending another night on the boat, pausing
  in the chapel, viewing the ward after treatment, and returning for the keys.
  The bone-turning ending is reachable through surrender inside the lorry.
- Preserved the existing cast, endings, save-node identifiers and meaningful
  choice effects. New entry effects are safe on Continue/Rewind. Existing saves
  remain usable, though previously visited passages may have new exits.
- The existing story audit now detects static cycles and repeated passages
  during its playthroughs. Verified all twelve endings and no reachable
  loops, dead ends, or missing links in 16,000 simulated walks.
- Trial runs also exposed inventory-dependent prose errors: the shop's window
  now offers a weapon the player can actually find, the Ferry Street fight
  accounts for whether the cutters were collected, and burning the lorry
  requires both alcohol and a lighter. Leaving Teddy no longer puts the
  revolver he keeps into the player's inventory.
- The first exposure day is recorded so triage can acknowledge a late arrival
  after a long boat stay rather than claiming every infection is three days old.
- Continue and Rewind now display saved passages without reapplying entry
  effects (including day advances, wounds and item grants). Ordinary forward
  choices still apply those effects once. Four deliberately different full
  routes were trialled; a browser trial confirmed Continue and Rewind leave
  day, visits and health unchanged, while a new choice still advances.
